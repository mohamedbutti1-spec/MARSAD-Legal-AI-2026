## Three tiers of gating

When a feature's data/logic is threaded through many routes with different access breadths, pick the tier per route rather than applying one blanket rule:

1. **Hard route lock** — route/route-group exists only to serve the feature (e.g. an admin-os tool, a dedicated court-simulation endpoint). Gate the whole route with a middleware (`requireShamsiOwner`) that does a generic 403 + audit log (`shamsi.access_denied`). No partial responses.
2. **Field-stripping on a legitimately broad route** — the route serves a different, broadly-accessible purpose (risk assessment, replay timeline, DCI-derived judicial/evidence exports) but one or more response fields are literally an output of the locked feature's methodology. Null out / redact just those fields for non-permitted roles; leave the rest of the payload intact. Do this at the route layer (or in a small shared helper), not in the data-shaping library code, so the "what gets shown to whom" decision stays visible in one place.
3. **Silent downgrade for id/lens selection** — a request parameter selects among several equivalent options (e.g. a lens id) and one option maps to the locked feature. Silently substitute a default/fallback rather than erroring, so a legitimate multi-option UI doesn't break for non-permitted roles.

**Why:** a hard lock on every route that merely *touches* the feature breaks legitimate broader workflows (e.g. general risk dashards, replay audit trails); a bare "hide the branding text" fix is not enough because the reviewer's real concern is *data* leakage, not just wording.

**How to apply:** for any "lock down feature X" task, enumerate every route that returns X-derived data (grep for the feature's field names, not just its display name), then classify each into one of the three tiers above before writing code.

## Scope boundary: branding vs. data

Generic platform-attribution/branding text naming the feature (e.g. a framework name in a PDF footer, a version string) is out of scope for redaction — it's product naming, not a data output. But any field that is a *direct output of the feature's methodology* — dimension scores, a compliance status computed from its criteria, per-index driver attribution tied to it — is in scope for stripping/gating even when it surfaces through an otherwise-legitimate broad-access route. When in doubt, treat the field as in-scope; the reviewer's stance is data-leak-focused, not branding-focused.

## When a "judge-only" or other broad-role feature turns out to BE the framework

Don't assume a feature is tier-2 (field-stripping) just because it looks like a generic judicial/legal tool. Check whether the feature's *entire output* is generated by prompting an AI to apply the locked framework as its core methodology (e.g. a review engine whose system prompt says "apply the Al-Shamsi Framework" and whose N analysis dimensions are literally the framework's N pillars). In that case there is no non-Shamsi content left to preserve — treat it as tier-1 (hard `requireShamsiOwner` lock on every route), not as a field to redact. Don't stack the feature's original role gate (e.g. `requireJudge`) together with `requireShamsiOwner` — if the two roles are mutually exclusive in the permission model, chaining both middlewares makes the route unreachable by anyone. Replace the old role gate outright, and update/hide the corresponding frontend tab so the now-locked role doesn't hit a wall of 403s.

## Watch for multiple identifier namespaces

The same concept can have more than one independent identifier in a codebase that grew over time (e.g. two different lens-id strings both meaning "the same theory/lens", used in different subsystems). A lock-down audit that greps for only one alias will silently miss the other. Grep for every known alias/spelling of the feature before declaring an audit complete, and re-grep after refactors that might introduce a new one.
